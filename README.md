# Задание 1. Анализ и планирование

### 1. Описание функциональности монолитного приложения

**Управление отоплением:**

- Пользователи могут управлять отоплением в доме выставляя значения температуры на определенном датчике по его id (Update Sensor Value)
- Система поддерживает проверку состояния всей системы через выделенный API (Health Check)
- Подключение и настройка датчиков отопления осуществляется специалистами поддержки через выделенный набор API:
	- Create Sensor - создает новый датчик отопления в опеределенном помещении с указанием используемых единиц измерения 
	- Update Sensor - изменяет конфигурацию существующего датчика (его местоположение или единицы измерения)
	- Delete Sensor - удаляет датчик из системы

**Мониторинг температуры:**

- Пользователи могут проверять температуру как на выделенном датчике по id (Get Sensor by ID) так и получать информацию о температуре со всех датчиков сразу (Get All Sensors)
- Система поддерживает получение информации о температуре через указание местоположения датчника

### 2. Анализ архитектуры монолитного приложения

- Язык программирования: Go
- База данных: Postgres 16
- В main.go запускается встроенный http сервер который принимает запросы по Rest API
- Внутри взаимодействие между компонентами осуществляется за счет синхронного вызова соответвующих go рутин
- Исключение представляет сервис получения данных о температуре, он регистрируется как внешний сервис и обращение к нему идет по rest api.
- Инициализация базы данных осуществляется отдельным init.sql скриптом

### 3. Определение доменов и границы контекстов

- Домен управления устройствами:
	- контектст: регуляция отопления
	- контекст: включение/выключение света
	- контекст: управление воротами
	- контекст: видеонаблюдение
	- контекст: пользовательское устройство (базовый API)
- Домен мониторинга системы:
	- контекст: сбор телеметрии
	- контекст: мониторинг состояния сенсеров
- Домент администрировния системы:
	- контекст: администрирование пользователей
	- контекст: управление сервисами
- Домен пользовательского сервиса (SaaS)
	- контекст: регистрация пользователя в системе
	- контекст: регистрация устройств в системе
	- контекст: настройка пользовательских сценариев


### **4. Проблемы монолитного решения**

- Единая кодовая база для всей функциональности приложения, которую по мере роста будет все сложнее поддерживать и вносить изменения
- Сложности с масштабированием решения, если какой-то сервис более требователен к ресурсам, масштабировать придется все приложение целиком
- Проблемы с поддержкой решения, если требуется выполнить какие-то сервисные работы, придется останавливать все приложение

# Задание 4. Создание и документирование API

### 1. Тип API

Для взаимодействия микросервисов я предполагаю использовать два типа API синхронный REST API и асинхронный посредством протокола MQTT.

Сихронный API будет применяться для большинства микросервисов: User SaaS API, Monitoring System API и Admin System API, так как они предполагают оперативное взаимодействие с пользователем системы и требуют оперативный ответ.

Для микросервиса управления устройствами (Manage Sensor API) я предлагаю использовать асинхронный API, так как данный сервис будет взаимодейтсвовать с приборами расположенными удаленно в домах пользователей за пределами локальной инфраструктуры и получить надежное сихронное взаимодейтсвие с ними затруднительно.

# Задание 5. Работа с docker и docker-compose

Перейдите в apps.

Там находится приложение-монолит для работы с датчиками температуры. В README.md описано как запустить решение.

Вам нужно:

1) сделать простое приложение temperature-api на любом удобном для вас языке программирования, которое при запросе /temperature?location= будет отдавать рандомное значение температуры.

Locations - название комнаты, sensorId - идентификатор названия комнаты

```
	// If no location is provided, use a default based on sensor ID
	if location == "" {
		switch sensorID {
		case "1":
			location = "Living Room"
		case "2":
			location = "Bedroom"
		case "3":
			location = "Kitchen"
		default:
			location = "Unknown"
		}
	}

	// If no sensor ID is provided, generate one based on location
	if sensorID == "" {
		switch location {
		case "Living Room":
			sensorID = "1"
		case "Bedroom":
			sensorID = "2"
		case "Kitchen":
			sensorID = "3"
		default:
			sensorID = "0"
		}
	}
```

2) Приложение следует упаковать в Docker и добавить в docker-compose. Порт по умолчанию должен быть 8081

3) Кроме того для smart_home приложения требуется база данных - добавьте в docker-compose файл настройки для запуска postgres с указанием скрипта инициализации ./smart_home/init.sql

Для проверки можно использовать Postman коллекцию smarthome-api.postman_collection.json и вызвать:

- Create Sensor
- Get All Sensors

Должно при каждом вызове отображаться разное значение температуры
